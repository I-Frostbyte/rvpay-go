# Clients Service API Architecture Review

Document Version: 1.0
Status: Approved
System: RVPay
Service: Clients Service
Review: Agent 04.5 — API Architecture Review

## 1. Purpose

This document records the comprehensive architectural review of the Clients
Service public API before repository implementation begins. The API is
considered frozen once this review is complete; future changes must be
additive only.

## 2. Review Scope

Reviewed:

- `protobuf/common.proto` — shared enums and messages.
- `protobuf/clients.proto` — Clients Service contract.
- Generated output in `grpc/go/commongrpc/` and `grpc/go/clientsgrpc/`.

Not inspected (per review scope):

- `clients/db/`, `deposits/db/`, `third_party/`, `tests/`, `vendor/`,
  `.github/`, `coverage/`, `bin/`, `tmp/`.

## 3. Strengths

### 3.1 Service Boundaries

- **ClientsService** owns client lifecycle (Create, Update, Delete, Get,
  List, Activate, Deactivate).
- **PlatformsService** owns the provider catalogue (List, Get, Enable,
  Disable).
- **IntegrationsService** owns provider installations (Install, Uninstall,
  Get, List, Reconnect, Disconnect, Sync).

Responsibilities are clearly separated with no overlap. No transaction-related
RPCs exist in the Clients Service.

### 3.2 RPC Design

- Every RPC name is clear and uses business terminology.
- Verbs are appropriate (Create/Update/Delete/Get/List/Activate/Deactivate/
  Install/Uninstall/Reconnect/Disconnect/Sync/Enable/Disable).
- Requests are minimal; responses are meaningful.
- No ambiguous or implementation-specific names.

### 3.3 REST Mappings

- Resource-oriented endpoints under `/v1/public/...`.
- Standard verbs: GET, POST, PATCH, DELETE.
- Custom actions use the `:verb` convention (`:activate`, `:deactivate`,
  `:enable`, `:disable`, `:reconnect`, `:disconnect`, `:sync`).
- Nested resource hierarchy supported for integrations under a client.

### 3.4 Messages and Enums

- No duplicate messages or enums.
- Consistent enum prefixes (`CLIENT_STATUS_`, `PLATFORM_STATUS_`,
  `INTEGRATION_STATUS_`, `OAUTH_STATUS_`, `WEBHOOK_STATUS_`,
  `PROVIDER_CAPABILITY_`).
- No reused field numbers; logical ordering; room for expansion.
- Shared objects (Pagination, Metadata, Audit, Error, Health) live in
  `commongrpc` and are reused where beneficial without premature abstraction.

### 3.5 Provider Independence

- No HighLevel or other provider is hardcoded anywhere in the contract.
- No provider-specific fields exist.
- OAuth implementation details are hidden.
- Future providers require implementation changes only — no protobuf redesign.

### 3.6 Documentation

- Every service, RPC, message, enum, and field carries meaningful
  business-purpose comments.
- No placeholder or autogenerated comments.

## 4. Issues Found and Resolved

### 4.1 Nested REST Binding for ListIntegrations

**Issue:** `ListIntegrations` exposed only the flat endpoint
`GET /v1/public/integrations`. The review guidance recommends resource
hierarchy support such as `/clients/{id}/integrations`.

**Resolution:** Added an `additional_bindings` entry to the
`ListIntegrations` HTTP annotation:

```proto
option (google.api.http) = {
  get : "/v1/public/integrations"
  additional_bindings {
    get : "/v1/public/clients/{client_id}/integrations"
  }
};
```

This is a minor HTTP path refinement. No messages, enums, field numbers, or
RPC signatures changed. The change is well under the 10% Approval Gate
threshold.
